# AI 协作开发协议

> 定义 AI（Claude 或任何 AI 助手）参与 lianyu-ai-core 项目时的行为规范。
> 这不是描述代码的文档，而是约束 AI 如何理解需求、分析影响、执行开发。

---

## 需求处理原则

收到开发需求时，**不要立即修改代码**。先判断：

1. **该需求属于哪个模块？**（参考 [ARCHITECTURE.md](ARCHITECTURE.md) 的模块职责表）
2. **是否符合当前架构设计？**（Persona → system.yaml、Memory → memory/、适配 → adapters/）
3. **是否会破坏已有模块职责？**（例如：不要在 adapters/ 中放 AI 逻辑）
4. **是否产生技术债？**（例如：不要在 ai/core.py 新增超过 20 行的方法）
5. **是否存在更合理的实现方式？**（先分析，再方案，再编码）

## 冲突处理规则

如果用户需求与项目架构文档冲突，**不要直接执行**：

1. 明确指出冲突位置（引用 ARCHITECTURE.md 的具体段落）
2. 说明可能造成的影响（影响范围分析）
3. 提供至少一个替代方案
4. 等待用户确认后再修改

**例外**：如果用户明确说"不用管架构、先实现再说"，可以先执行但记录为技术债。

## 修改优先级

```
项目长期目标 > 系统架构一致性 > 开发规则 > 用户当前需求 > 性能优化 > 代码美观
```

**不要为了满足单次需求破坏长期架构。**

示例：
- 用户说"给 Telegram Bot 加一个自动回复" → 不应该直接在 `bot.py` 中硬编码回复逻辑。应该走 `ai/core.py` 的标准消息处理流程。
- 用户说"快速加一个功能" → 即使快速，也不能跳过影响分析。快是指编码阶段快，不是跳步。

## 核心模块保护

以下模块**修改前必须先输出影响分析**：

| 模块 | 原因 | 分析要求 |
|------|------|---------|
| `ai/core.py` | 1122 行中枢 | 分析：此逻辑能否独立成模块？影响哪些调用方？ |
| `memory/stores/` | 数据持久化入口 | 分析：是否需要 DB 迁移？是否影响已有数据？ |
| `database/models/` | ORM 表结构 | 分析：ALTER TABLE 方案？已有数据兼容性？ |
| `prompt/templates/system.yaml` | Persona 行为 | 分析：是否改变语气？是否新增"不要 X"式黑名单？ |
| `adapters/telegram/bot.py` | 生产入口 | 分析：是否需要重启服务？是否影响消息处理？ |

## 需求冲突检查（收到新需求时）

收到开发需求时，AI **不允许立即写代码**。必须先检查：

1. 是否违反 [PROJECT_OVERVIEW](PROJECT_OVERVIEW.md)（项目目标、不做什么）？
2. 是否违反 [ARCHITECTURE](ARCHITECTURE.md)（模块职责边界、数据流）？
3. 是否违反 [ARCHITECTURE_DECISIONS](ARCHITECTURE_DECISIONS.md)（已有设计决策）？
4. 是否违反 [DEVELOPMENT_RULES](DEVELOPMENT_RULES.md)（开发规则、核心保护）？
5. 是否违反本协议（AI 协作约定）？

如果**存在冲突**：
1. 明确指出冲突位置（引用具体文档和段落）
2. 解释如果不处理冲突可能造成的风险
3. 提供至少一个替代方案
4. 等待用户确认后再修改

如果**无冲突**：继续走开发流程。

## 开发流程

### 普通修改（如调整 system.yaml、修改 memory/ 非 Store 文件）

```
需求 → 影响分析（口述 1-2 句）→ 实现 → pytest → 完成
```

### 重大修改（如修改 ai/core.py、新增模块、数据库 schema 变更）

```
需求 → 架构评估（输出书面分析）→ 设计方案 → 用户确认 → 编码 → pytest + 实际观察 → 更新 CHANGELOG + V3_STATUS
```

## 开发结束 Checklist

每次开发完成后，自动输出：

```
【Documentation Checklist】
1. 本次修改影响哪些模块？           → [模块名]
2. 是否新增架构？                   → 是/否
3. 是否修改模块职责？               → 是/否
4. 是否产生新的设计决策？           → 是/否（如果是 → 新增 ADR）
5. 是否需要记录到 CHANGELOG？        → 是/否
6. 是否需要更新 V3_STATUS？         → 是/否
7. 是否需要更新 ARCHITECTURE？       → 是/否
8. 是否需要新增 ADR？                → 是/否
```

并据此主动更新相关文档。

## 版本冻结机制

当版本进入稳定阶段（如当前 V3.7）：

**默认禁止**：
- 新增核心功能
- 新增模块
- 数据库 schema 变更
- 架构重构

**允许**：
- Bug 修复
- 表达层微调（system.yaml ≤ 10 行/次）
- 稳定性优化
- 文档完善

**如需新增大型功能**（如 Emotion、Vision、Agent、Voice、多角色）：
- 在 V3_STATUS.md 中标记"计划中（V4）"
- 不在当前冻结版本中实现
- 开启新版本规划后方可实施

---

## 稳定化阶段规则（当前 V3.7）

在当前 V3.7 稳定化阶段：

- **默认行为**：只读分析，不修改代码
- **允许**：数据库状态检查、日志分析、表达观察
- **禁止**：新功能、重构、Prompt 规则变更
- **如需修改**：先输出修改方案 → 等确认 → 再编码

## 部署与 Git 规则

- **不自动 git push**
- **不自动部署服务器**
- **不自动修改服务器文件**
- 涉及服务器同步的操作**必须先确认**
- `.env` 不提交到 Git（已在 `.gitignore`）
- `archives/`、`data/`、`logs/` 是运行数据，不作为代码同步

## 开发环境 vs 生产环境

| | 主机（开发） | 服务器（生产） |
|------|------------|-------------|
| 路径 | `E:\Visual Studio Code文件\lianyu-ai-core` | `E:\AI\lianyu-ai-core` |
| 职责 | 开发、测试、改 Prompt | 运行服务、看日志 |
| 代码修改 | ✅ 允许 | ❌ 禁止 |
| 数据库 | 测试数据 | 生产数据 |

**开发修改默认在主机进行。** 永远不要直接修改服务器文件。
